Where the contextactually goes — and which fixes are real.

Boot context is already near its floor; almost all of it is platform overhead you can't touch. The fight that's left is mid-session — big file reads, verbose agent and tool returns, long shell output, compaction churn. Five probes across native features, community tooling, workflow habits, delegation economics, and abandoned anti-patterns converge on one quiet conclusion: the wins are behavioural and nearly free, and most of the tools you could install are a wash.

01 — The drain moved

The cleanup already won. The cost is elsewhere.

At load, ~15% of a 200k window is gone — but ~68% of that is Anthropic-fixed system prompt and tool schemas, and the slice genuinely under your control is about 1.5% of the window. Pruning more agents and skills is finished work with diminishing returns.

So the question stops being "what's loaded at boot" and becomes "what bloats the window while I work." That drain has four named sources: a single full read of a large file, a subagent or tool that returns its whole transcript, an unfiltered shell dump, and lossy /compact churn that quietly drops your conventions. None of them are config — they're how the session is driven.

The shape of it

Boot context is a solved, near-floor problem. Mid-session context is an unsolved, behavioural one. Everything below is about the second.

You already own the biggest lever

Subagent isolation — pushing read-heavy and exploratory work into a child window so only a short answer returns — is the single highest-impact technique in every probe. Your worker / reviewer / researcher setup is exactly this. The rest is incremental.

The tell

Every "Skip" row is something you'd install; every "Works" row is something you'd do. The same MCP tools that save read-tokens add per-turn tool-definition tax that several sources flag as a wash on small repos. On a lean solo setup, no-install beats always-on almost every time.

03 — Delegation economics

The firewall, and what it really costs.

Subagents save main-thread context and cost more total tokens — both true at once. You spend cheap, disposable child-window tokens to protect the one scarce resource: your main thread's attention.

15×
Multi-agent vs a chat message — the scary figure, in context
3–4×
Honest multiplier vs a normal single-agent session
80%
Of performance variance explained by token spend alone
44%
Of multi-agent failures are system-design / spec (MAST)

The widely-quoted "15× tokens" is multi-agent versus a single chat message — not versus a coding agent. Against your normal single-agent session the real multiplier is roughly 3–4×. You're not being wasteful; you're buying main-thread cleanliness and wall-clock (parallel fan-out cut research latency up to 90%) with cheap child tokens.

Delegate when

Work is independent / breadth-first / noisy / read-heavy and a short summary suffices — research, parallel lookups, throwaway exploration, anything that would otherwise dump raw text into your window.

Stay single-thread when

Work is sequential, decision-dense, or shares one mutable artifact — coding, refactors, anything where two children could make conflicting choices. Cognition's "Flappy Bird becomes Mario" failure is exactly this.

"Most coding tasks involve fewer truly parallelizable tasks than research." Anthropic and Cognition don't actually disagree — they disagree on task type, and both land on: keep dependent / coding work single-threaded. — Anthropic, Building a multi-agent research system · Cognition, Don't Build Multi-Agents, 2025
Where your leverage actually is

MAST found 44% of multi-agent failures are bad orchestration and specs, not weak models. The fix a solo dev fully controls: tight task scopes and explicit done-conditions on every delegated child. That's a habit, not a tool.

04 — Abandoned anti-patterns

What the community stopped doing.

A watch-list, not a chore-list. These are the moves that quietly bloat context and have already been corrected away in 2025–2026 practice. Recognise them so you don't drift back into one.

Eager-loading many MCP servers

Each server injects large tool schemas at startup — the "MCP context bloat" complaint. Replaced by on-demand / deferred tool loading and pruning to the few servers a session needs.

Oversized CLAUDE.md / AGENTS.md

Mega-prompts of rules make agents fragile and unpredictable. Replaced by lean files that link out to scoped references — context as a curated budget, not a dumping ground.

Too many always-on skills / agents

Every description loads each turn. Replaced by progressive disclosure (only the matched body loads), short descriptions, and isolating work in subagents.

Over-aggressive /compact

Compaction amnesia silently drops conventions. Replaced by fresh-session-over-compact plus durable memory in files re-read on demand.

Dumping whole large files

All-or-nothing reads waste thousands of tokens. Replaced by line-ranged reads and search-first retrieval — a 15k read becomes ~500 targeted tokens.

Giant unfiltered tool / test output

Raw logs pollute the retrieval loop. Replaced by narrow searches and condensed subagent digests (1–2k tokens, not raw dumps).

The one that underwrites all of them: context rot

"More context = better" is false. The reason every anti-pattern above is an anti-pattern is that attention is not uniform across a long window.

The softening edge

One nuance to hold loosely: compaction is being actively improved (faster, smarter preservation in recent CC versions), so "always prefer a fresh session" is drifting toward "durable memory + selective compaction." Don't treat the blanket ban as permanent.

If you only ever do one thing

Keep subagent returns terse. It's the cheapest move that protects the lever you already built — and it's the one most likely to quietly erode if left unspecified.

Explicitly not worth it here

No persistent-memory layer, no context-compression MCP stack, no skill-budget knobs, no extra always-on servers. For a lean solo setup they add tax or friction for a wash.
