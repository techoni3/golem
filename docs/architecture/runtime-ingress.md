# Durable runtime ingress

GOL-34 keeps runtime producers outside SQLite. A producer validates a GOL-26 `RuntimeSignalV1` and writes only beneath its temporary or service-owned `GOLEM_HOME/inbox`: a private temporary file is fsynced, atomically published without clobbering an existing event id, and the directory is fsynced. The authenticated control-plane `POST /api/v1/runtime/events` is the equivalent ingress; it receives only the spool port, never a persistence handle.

The one service owner claims `pending` files by rename into `processing`. It validates schema/version and size before dispatching to an explicitly registered, pure materializer handler. A short persistence transaction records the raw source event/dedupe key, producer watermark, canonical mutation, explanation diagnostic, and optional `runtime_outbox` record. Only after that commit does it archive the source. A restart reclaims leftover processing entries; a committed-but-unarchived source is deduplicated and archived rather than materialized twice. Malformed, unknown-version, oversized, or unregistered signals go to `quarantine` and cannot block later work.

`runtime_outbox` remains an at-least-once boundary. The drainer leases bounded claims, gives the stable outbox id to its destination as the idempotency key, and acks only after that destination returns. A service-down or consumer-crash failure receives existing bounded retry/backoff semantics; exhausted records retain observable permanent-failure metadata. Inbox metrics expose only pending/processing/archive/quarantine counts and age—never payloads, tokens, or other secrets.

The compact real J3 `materializer-crash-matrix` is the regression proof: 100 concurrent producers plus duplicates, child-process crash positions, restart dedupe, stale watermarks, malformed quarantine, and an independent SQLite consumer crash/replay. `dashboard-down-inbox-replay` intentionally reuses that one journey because the cross-store service-down replay is the same executable boundary, not a second mock suite.
